The Overarching Philosophy

Go's I/O is not a framework. It is a composition system built on two tiny interfaces. The entire standard library, every third-party package that does I/O — all of it flows through these two shapes:

Source
→
io.Reader
→
Transform(s)
→
io.Writer
→
Destination

Sources that implement Reader: files, sockets, strings, byte slices, HTTP bodies, compressed streams, pipes.
Destinations that implement Writer: files, sockets, HTTP responses, buffers, loggers, gzip compressors.
Transforms wrap a Reader/Writer and modify data in-flight: buffering, compression, rate-limiting, hashing.

🔑
The Golden Rule: In Go, you never invent a new I/O API. You compose existing Readers and Writers. This is why Go code for "read a gzip'd file over HTTP and stream to disk" is ~10 lines instead of 200.

Why These Exact Signatures?
// the most important question in Go I/O — derive it from first principles

The Reader Signature

// Actual Go stdlib definition type Reader interface { Read(p []byte) (n int, err error) } // Alternative that Go deliberately REJECTED // Read() []byte ← why is this wrong?

This is not an arbitrary choice. Every element of the signature encodes a hard systems constraint. Let's derive each one.

Why caller-owned buffer: Read(p []byte)?

If Go had chosen Read() []byte, the implementation would have to allocate a new slice for every call. Consider what happens on a network socket serving 10,000 connections:

// BAD: Read() []byte — what would happen internally func (conn) Read() []byte { buf := make([]byte, ?) // HOW LARGE? Don't know yet. n, _ := syscall.Read(fd, buf) return buf[:n] // Allocation every call. GC pressure. } // GOOD: Read(p []byte) — caller controls everything func (conn) Read(p []byte) (int, error) { n, err := syscall.Read(fd, p) // Direct into caller's buffer. Zero alloc. return n, err }
Read() []byte — Problems
• Allocates on every call → GC pressure
• Implementation guesses buffer size
• Caller can't reuse memory
• Can't do zero-copy (e.g. scatter-gather I/O)
• Ownership is ambiguous — who frees?
Read(p []byte) — Properties
• Caller pre-allocates, reuses across calls
• Caller controls read granularity (8B to 64KB)
• Zero allocation hot path
• Direct syscall mapping (read(2) takes fd + buf + len)
• Ownership is explicit — caller owns p

Why return (n int, err error) instead of just ([]byte, error)?

⚠️
Partial reads are not errors. This is the single hardest thing for beginners to internalize. When you call Read(buf) with a 4096-byte buffer on a TCP socket, you might get 1 byte back. That is not an error. That is how the kernel works. The n return value tells you how many bytes actually landed in your buffer.
// Why n matters — partial read example on a socket buf := make([]byte, 4096) n, err := conn.Read(buf) // n might be 1, 17, 4096, or anything in between. // This is NOT a bug. TCP is a byte stream, not a message stream. // err == nil + n == 0 can happen (non-blocking sockets) // err == io.EOF means the other side closed the connection // Correct: loop until you have what you need func readExactly(r io.Reader, n int) ([]byte, error) { buf := make([]byte, n) _, err := io.ReadFull(r, buf) // handles the loop for you return buf, err }

Why (n int, err error) can both be non-zero simultaneously

n, err := r.Read(buf) // Case 1: n=10, err=nil — read 10 bytes, more data exists // Case 2: n=10, err=io.EOF — read final 10 bytes, stream ended (VALID!) // Case 3: n=0, err=io.EOF — stream already exhausted // Case 4: n=0, err=someErr — actual error, no data // Case 5: n=5, err=someErr — partial read before error (treat as data!) // WRONG pattern (misses case 2): if err != nil { return } process(buf[:n]) // CORRECT pattern: process(buf[:n]) // process first, even if err != nil if err == io.EOF { break } if err != nil { return err }

The Writer Signature

type Writer interface { Write(p []byte) (n int, err error) }

Why return n on Write?

Partial writes happen in the kernel. You ask to write 4096 bytes to a socket, the kernel sends 2048 because its send buffer is full. This is called a short write. Without n, you'd never know it happened.

// The io.Writer contract says: if n < len(p) AND err == nil, that's a BUG in the impl // But YOU still need to check n when layering on raw syscalls func writeAll(w io.Writer, data []byte) error { for len(data) > 0 { n, err := w.Write(data) data = data[n:] // advance past what was written if err != nil { return err } } return nil } // This pattern is exactly what io.WriteString does internally
🔑
The kernel model. Linux's read(2) syscall signature is ssize_t read(int fd, void *buf, size_t count). Go's Read(p []byte) (int, error) is a direct thin mapping over this. Go chose to preserve syscall semantics rather than hide them. This is intentional — hiding them creates bugs.

io.Reader — How Any Implementation Works

When you call f.Read(buf) on an os.File, here is the exact call chain from your Go code to the kernel and back:

f.Read(buf)
→
file.go pread()
→
syscall.Syscall
→
SYS_READ (Linux)
→
VFS → FS driver

The Go scheduler's interaction here is critical: when SYS_READ blocks (data not ready), the Go runtime parks the goroutine and runs another goroutine on the same OS thread. This is what makes Go I/O appear non-blocking at the user level while remaining blocking at the goroutine level.

// os.File.Read — simplified internal path func (f *File) Read(b []byte) (n int, err error) { if err := f.checkValid("read"); err != nil { return 0, err } if n, e := f.read(b); e != nil { err = f.wrapErr("read", e) } return n, err } // f.read() eventually calls poll.FD.Read() which calls // syscall.Read(fd, p) — which is the raw SYS_READ syscall

io.ReadAll — Internally

// Actual implementation from Go stdlib (simplified) func ReadAll(r Reader) ([]byte, error) { b := make([]byte, 0, 512) // start with 512 byte capacity for { n, err := r.Read(b[len(b):cap(b)]) b = b[:len(b)+n] if err != nil { if err == EOF { err = nil } return b, err } if len(b) == cap(b) { // buffer is full, grow it (doubles) b = append(b, 0)[:len(b)] } } } // Key insight: it uses the slice trick b[len:cap] to avoid // zeroing bytes. It reads directly into pre-allocated capacity.
⚠️
ReadAll danger zone. On an HTTP response body, ReadAll will happily consume 2GB into RAM. Always pair with io.LimitReader for untrusted inputs: io.ReadAll(io.LimitReader(resp.Body, 10<<20)) — caps at 10MB.

io.Copy — The Zero-Copy Fast Path

This is where Go gets clever. io.Copy is not just a loop over Read/Write. It checks if the source or destination implements special interfaces that enable OS-level zero-copy:

// io.Copy internal decision tree (simplified) func Copy(dst Writer, src Reader) (int64, error) { // Fast path 1: src implements WriteTo(dst) — e.g. *os.File if wt, ok := src.(WriterTo); ok { return wt.WriteTo(dst) // os.File.WriteTo can call sendfile(2) syscall! // Data NEVER leaves kernel space — zero copy to userspace } // Fast path 2: dst implements ReadFrom(src) — e.g. *net.TCPConn if rt, ok := dst.(ReaderFrom); ok { return rt.ReadFrom(src) } // Slow path: manual loop with 32KB buffer buf := make([]byte, 32*1024) for { nr, er := src.Read(buf) if nr > 0 { dst.Write(buf[:nr]) } if er == EOF || er != nil { break } } } // sendfile(2): copies from file fd to socket fd INSIDE the kernel // This is how nginx/caddy serve static files at ~40GB/s on modern hardware
🔑
Zero-copy path. When you do io.Copy(conn, file) — file → TCP socket — Go can use the Linux sendfile(2) syscall. Data goes from disk buffer cache directly to the socket send buffer inside the kernel. Your Go code never touches the bytes. This is how HTTP file servers achieve near wire-speed.

Buffered I/O — Why Syscalls Are Expensive
// bufio.Reader, bufio.Writer — batch kernel round-trips

The Problem Buffering Solves

Every Read() or Write() call on an unbuffered source (file, socket) is a syscall. Syscalls are expensive because they require a context switch from user space to kernel space and back:

SYSCALL COST VISUALIZATION — reading "Hello\nWorld\nFoo\n" character by character vs buffered
Unbuffered (18 reads)
18 syscalls
Buffered (1 read)
1 syscall
Each syscall: ~100-300ns context switch overhead. At 100k calls/sec = 10-30ms wasted per second per goroutine.

bufio.Reader — Internal State

A bufio.Reader wraps any io.Reader and maintains an internal byte buffer (default 4096 bytes). It refills this buffer in large chunks, then serves your small reads from it without touching the kernel:

// bufio.Reader internal structure (from bufio/bufio.go) type Reader struct { buf []byte // the internal buffer (default 4096 bytes) rd io.Reader // the underlying reader (file, socket, etc) r, w int // r=read position, w=write position in buf err error lastByte int // for UnreadByte lastRuneSize int // for UnreadRune } // When buf[r:w] is empty, it calls rd.Read(buf) to refill. // Your small Read() calls serve from buf[r:w] without syscalls.

bufio.Writer — Flush or Lose Data

// bufio.Writer internal structure type Writer struct { err error buf []byte // accumulates your writes n int // how many bytes are in buf wr io.Writer // underlying writer (file, socket) } // When n == len(buf): auto-flushes (calls wr.Write(buf[:n])) // You must call Flush() at the end to drain any partial buffer // Classic bug: forget Flush() → last few KB silently lost w := bufio.NewWriter(file) w.WriteString("hello") w.WriteString(" world") // ← if you return here without Flush(), nothing is written to disk defer w.Flush() // ALWAYS defer this immediately after NewWriter

Special Powers of bufio.Reader (vs raw io.Reader)

Peek internals. Peek(n) is how you implement protocol parsers without consuming bytes. It calls fill() if needed to ensure at least n bytes are in the buffer, then returns buf[r:r+n]. This slice is only valid until the next Read call — it's a window into the buffer, not a copy.
bufio.Scanner — Tokenized Reading
// the right tool for line-by-line and word-by-word iteration

Internal Architecture

Scanner is a thin layer on top of bufio.Reader logic. Internally it maintains a buffer and a SplitFunc — a function that looks at the current buffer contents and decides where one token ends.

// The SplitFunc signature — the heart of Scanner type SplitFunc func( data []byte, // unprocessed data in the buffer atEOF bool, // true when underlying reader is exhausted ) ( advance int, // how many bytes to consume from data token []byte, // the token to return (nil means "need more data") err error, ) // Built-in SplitFuncs: // bufio.ScanLines — splits on \n (strips trailing \r\n) // bufio.ScanWords — splits on whitespace // bufio.ScanBytes — one byte per token // bufio.ScanRunes — one UTF-8 rune per token
// How Scanner.Scan() works internally (simplified) func (s *Scanner) Scan() bool { for { // 1. Try to find a token in what we already have buffered advance, token, err := s.split(s.buf[s.start:s.end], s.done) if token != nil { s.token = token s.start += advance return true } // 2. No token yet — read more data from underlying reader n, err := s.r.Read(s.buf[s.end:]) s.end += n // handle err, EOF, buffer growth... } }

🔴
The 64KB token limit trap. Scanner has a default max token size of 64 * 1024 bytes. If you scan a log file with a line exceeding this, Scan() returns false and Err() returns bufio.ErrTooLong. Fix: call scanner.Buffer(make([]byte, 1<<20), 1<<20) to set a 1MB limit before the first Scan().

Custom SplitFunc Example — CSV Field Tokenizer

// Custom split: extract comma-separated tokens splitCSV := func(data []byte, atEOF bool) (int, []byte, error) { for i, b := range data { if b == ',' { return i + 1, data[:i], nil // advance past comma, return field } } if atEOF && len(data) > 0 { return len(data), data, nil // last field, no trailing comma } return 0, nil, nil // need more data } scanner := bufio.NewScanner(r) scanner.Split(splitCSV) for scanner.Scan() { fmt.Println(scanner.Text()) }

json.Decoder vs json.Unmarshal — Crucial Difference

// json.Unmarshal — reads ALL bytes first, then parses data, _ := io.ReadAll(file) var v MyStruct json.Unmarshal(data, &v) // entire file must fit in RAM // json.Decoder — streams, decodes token by token dec := json.NewDecoder(file) for dec.More() { var item Item dec.Decode(&item) // reads ONLY what's needed for one item process(item) } // 100GB JSONL file? Decoder handles it. Unmarshal crashes.

json.Decoder Internal State Machine

Internally, json.Decoder maintains a scanner that reads one rune at a time from its buffered reader, building a state machine to identify JSON token boundaries (strings, numbers, objects, arrays). It only allocates when it needs to return a complete token.

encoding/binary — For Protocol Buffers and Binary Formats

// binary.Read — reads exactly sizeof(v) bytes, interprets per endianness var header struct { Magic [4]byte Version uint16 Length uint32 } err := binary.Read(r, binary.LittleEndian, &header) // Internally: calls io.ReadFull(r, buf[0:unsafe.Sizeof(header)]) // Then uses unsafe/reflect to fill each field respecting byte order // This is how you parse TCP frames, file headers, ELF binaries
💡
Prefer manual field reads for hot paths. binary.Read uses reflection, which allocates. For high-throughput binary parsing (e.g. in your WebSocket broadcast server), manually read fields with io.ReadFull and byte-slice indexing + binary.LittleEndian.Uint32(buf[4:8]) — zero allocation, zero reflection.
Random Access — ReadAt, WriteAt, Seek
// for binary formats, databases, and indexed access patterns

The Fundamental Difference

Sequential readers maintain a cursor that advances as you read. Random access lets you read from any position at any time. There are two approaches, with very different concurrency properties:

// Approach 1: Seek + Read — moves the cursor, then reads f.Seek(1024, io.SeekStart) // set cursor to byte 1024 f.Read(buf) // read from cursor position // PROBLEM: Seek then Read is NOT atomic // Concurrent goroutine can Seek to a different position between your calls // Approach 2: ReadAt — single atomic operation, no cursor change f.ReadAt(buf, 1024) // read from offset 1024 // Internally: pread64(fd, buf, len, offset) — ONE syscall, cursor untouched // Safe to call from multiple goroutines concurrently on the same *os.File

Syscalls per operation2 (lseek + read)1 (pread64)

Seek Whence Values — What They Mean

// Three seek modes map directly to Linux lseek() whence parameter f.Seek(0, io.SeekStart) // absolute: go to byte 0 (SEEK_SET) f.Seek(100, io.SeekCurrent) // relative: advance 100 bytes (SEEK_CUR) f.Seek(0, io.SeekEnd) // from end: f.Seek(0, End) = EOF position f.Seek(-8, io.SeekEnd) // last 8 bytes of file (SEEK_END) // Get current position without moving cursor: pos, _ := f.Seek(0, io.SeekCurrent) // Get file size: size, _ := f.Seek(0, io.SeekEnd) f.Seek(0, io.SeekStart) // reset to start afterward

Composition — The Real Power of Go I/O
// TeeReader, MultiReader, Pipe, LimitReader — building data pipelines

io.TeeReader — Read While Duplicating

// TeeReader wraps a reader. Every byte read from it is ALSO written to w. func TeeReader(r Reader, w Writer) Reader { return &teeReader{r, w} } func (t *teeReader) Read(p []byte) (n int, err error) { n, err = t.r.Read(p) if n > 0 { t.w.Write(p[:n]) } // mirror to w return } // Real use case: compute hash while processing HTTP body h := sha256.New() tee := io.TeeReader(resp.Body, h) // every read also goes to hasher json.NewDecoder(tee).Decode(&response) digest := h.Sum(nil) // hash of exactly what we read, computed in-flight

io.MultiReader — Virtual Concatenation

// MultiReader presents multiple readers as one sequential stream header := strings.NewReader("--boundary\r\nContent-Type: text/plain\r\n\r\n") body := file // actual file data footer := strings.NewReader("\r\n--boundary--\r\n") combined := io.MultiReader(header, body, footer) // combined looks like one Reader. When header exhausts, body starts. No copying. // This is exactly how HTTP multipart form uploads work. http.Post(url, "multipart/form-data", combined)

io.MultiWriter — Fan-Out Writing

// Every Write() call is replicated to all writers logFile, _ := os.Create("app.log") w := io.MultiWriter(os.Stdout, logFile) log.SetOutput(w) // now logs go to both stdout AND file simultaneously // Internally: Write(p) calls each writer in sequence. First error stops.

io.Pipe — Synchronous Goroutine Bridge

Pipe is often misunderstood. Unlike bytes.Buffer, it has zero internal storage. A Write blocks until someone Reads. They rendezvous at the byte boundary.

pr, pw := io.Pipe() // Writer goroutine go func() { json.NewEncoder(pw).Encode(largeStruct) // blocks until consumer reads pw.Close() }() // Reader goroutine (or main) gzip.NewReader(pr) // reads from the pipe, unblocking the encoder above // No intermediate buffer! Data flows directly between goroutines. // Memory: O(one Write call), not O(entire stream)
🔑
Pipe vs bytes.Buffer. Use io.Pipe when you want streaming with zero buffering and goroutine synchronization. Use bytes.Buffer when you want to accumulate then read (single goroutine, or with external locking). Pipe is the right choice when producer and consumer run concurrently and you want backpressure — if the consumer is slow, the producer blocks automatically.

io.LimitReader — Security Boundary

// LimitReader returns a Reader that reads at most n bytes limited := io.LimitReader(resp.Body, 10<<20) // 10MB cap data, _ := io.ReadAll(limited) // Without this: malicious server sends ∞ bytes, ReadAll eats all RAM // Internal: it's just a struct with a counter type LimitedReader struct { R Reader; N int64 } func (l *LimitedReader) Read(p []byte) (int, error) { if l.N <= 0 { return 0, EOF } if int64(len(p)) > l.N { p = p[:l.N] } n, err := l.R.Read(p) l.N -= int64(n) return n, err }

The Critical Question: Why gzip → buffer → conn, not buffer → gzip → conn?

🤔
This ordering question is the deepest test of pipeline intuition. The answer comes from understanding what each layer sees as its "upstream".
❌ WRONG: buffer → gzip → conn
Buffer accumulates uncompressed data → flushes a chunk → gzip compresses that chunk.

Problem: gzip compresses small chunks separately. Each chunk is a separate deflate block. Compression ratio drops 30-50% because gzip's dictionary (back-reference table) resets between chunks. You lose the cross-chunk pattern matching that makes compression work.
✅ CORRECT: gzip → buffer → conn
Gzip sees the full uncompressed stream → produces compressed bytes → buffer accumulates those compressed bytes → one Write() to the network.

Benefit: gzip maintains its dictionary across all your writes. Compression ratio is maximized. Buffer batches the small compressed outputs into one network syscall.
// CORRECT pipeline: data → gz → buf → conn buf := bufio.NewWriterSize(conn, 64*1024) gz := gzip.NewWriter(buf) // gz writes compressed bytes INTO buf // buf absorbs gz's small compressed writes, sends one big network write gz.Write(data) // your uncompressed data goes in here gz.Close() // flushes gzip stream (writes final block to buf) buf.Flush() // flushes buf to conn (one network syscall) // Rule of thumb: producers (data transformers) go CLOSER to the source. // Consumers (batchers, senders) go CLOSER to the destination.

The Four Most Common Mistakes

1. Ignoring partial reads
Calling Read(buf) once and assuming buf is fully populated. Use io.ReadFull or loop explicitly for binary protocols.
2. Forgetting bufio.Writer.Flush()
The last writes silently never reach disk or network. Always defer w.Flush() immediately after bufio.NewWriter().
3. ReadAll on large/infinite streams
HTTP bodies, log tails, WebSocket frames — none should be ReadAll'd. Always combine with LimitReader or stream with Scanner/Decoder.
4. Seek+Read in concurrent code
Two goroutines doing Seek+Read on the same *os.File will race. Use ReadAt or open separate file descriptors.
