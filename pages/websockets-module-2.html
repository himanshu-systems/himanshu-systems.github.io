Part 09 — Browser Internals

The socket isn't where your JS runs

Modern browsers are multi-process. A sandboxed renderer runs your JavaScript on a single main thread; a privileged network process owns the actual sockets. WebSocket bytes are read in the network process and shipped over IPC to the renderer, where each message is queued as a task on the event loop. Your onmessage never preempts — it runs between other tasks.

Chromium architecture — where a frame becomes an onmessage call
┌─────────────────── NETWORK SERVICE PROCESS (privileged) ───────────────────┐ │ owns TCP/TLS socket · reads bytes · WS frame parser · un-mask N/A │ │ (server→client frames are unmasked) ▼ │ └──────────────────────────────── Mojo IPC ──────┼───────────────────────────┘ ▼ ┌─────────────────── RENDERER PROCESS (sandboxed, per-site) ─────────────────┐ │ MAIN THREAD ─ single event loop: │ │ [ task ][ task ][ MESSAGE EVENT ][ task ][ rAF ][ MESSAGE EVENT ] ... │ │ if a task runs 200ms, every queued message waits 200ms ──┐ │ │ ws.onmessage(e) runs here ◄───────────────────────────────────┘ │ │ ws.send(x) → copies into network process's SEND buffer (never blocks) │ └─────────────────────────────────────────────────────────────────────────────┘
The main thread processes one task at a time. A long task starves message delivery even though the bytes already arrived in the network process.

Why split processes

Security (sandbox can't touch raw sockets/fs), stability (a network crash doesn't kill your tab), site isolation. Cost: every message crosses an IPC boundary.

Backpressure footgun

ws.send() never blocks — it buffers in memory. On a slow uplink, unbounded sends grow ws.bufferedAmount until the tab OOMs. You must gate on bufferedAmount yourself.

Use a Worker

WebSocket works in Web Workers — move parsing/serialization off the main thread so a busy UI doesn't stall delivery, and a flood of messages doesn't jank rendering.

Limits & throttling

Chrome caps ~255 WS per host (separate from the 6 HTTP/1.1 limit). Background tabs get throttled — heartbeats may lag, triggering false disconnects.

Part 10 — Server Internals

C10K → C10M: stop giving each connection a thread

A WebSocket connection is mostly idle — it waits. The naive model gives each connection a thread blocked in read(). At a million connections that's a million thread stacks and a scheduler in meltdown. The fix is readiness notification: a few threads ask the kernel "which of these N sockets have data right now?" — epoll (Linux), kqueue (BSD/macOS), IOCP (Windows, completion-based).

epoll is O(ready), not O(N)

epoll_wait() returns only the fds with events — cost scales with active connections, not total. select()/poll() rescan all N every call → die past ~1024 fds.

If you removed it

Thread-per-conn at 1M: ~1M × 512 KB stacks ≈ 512 GB of stacks, plus context-switch storms. The machine falls over long before the network does.

Edge vs level-triggered

Level-triggered keeps notifying while data remains (simpler). Edge-triggered notifies once per readiness edge → you must drain fully or you hang. Classic 3 AM bug.

Part 11 — Scaling Across Machines

Statefulness is the whole problem

A connection lives on one gateway process. To deliver "user A messaged room R" to A's 10,000 followers spread across 50 gateways, every gateway must learn of the event. That requires a shared message bus and a fan-out strategy. The load balancer's job is stickiness: route a client's handshake (and reconnects) to a node that can serve it; the single long-lived TCP connection then pins itself to that node automatically.

Hot channel = hotspot

A celebrity or a popular trading symbol concentrates fan-out on a few nodes. Fixes: shard channels, dedicate nodes to hot topics, or tree/hierarchical fan-out.

WhatsApp / Discord

Erlang/Elixir on the BEAM — millions of lightweight processes per box, one per connection, built-in supervision. Discord shards "guilds"; Rust on hot paths.

Trading (Binance / Kite)

Latency-obsessed market-data fan-out, often per-symbol sharding and snapshot+delta streams; internal transport may be multicast/UDP, WS at the edge.

Part 12 — Reliability & Failure

The connection that's dead but doesn't know it

A cut cable, a crashed peer, or a NAT box silently dropping its mapping leaves a half-open connection: one side is gone, the other thinks it's fine. TCP won't tell you for ~2 hours. The only cure is application heartbeats — WebSocket Ping (0x9) / Pong (0xA) control frames. Send a Ping every T seconds; no Pong within the window → declare dead and close. (Browsers auto-reply to Ping; from JS you can't send a Ping, so apps often add their own ping message.)

Thundering herd

All clients reconnect at once → a self-inflicted SYN+TLS+handshake flood that re-kills the server you just restarted. Backoff with jitter de-synchronizes them.

No built-in resume

Unlike SSE's Last-Event-ID, WebSocket has no resumption. You build it: per-message IDs, client sends "last seen" on reconnect, server replays from a buffer, client dedups. Design for at-least-once + idempotency.

Graceful shutdown

On deploy: stop accepting, send Close 1001 going away, drain, and stagger so clients don't all reconnect on the same millisecond.

Part 13 — Security

Cross-Site WebSocket Hijacking

The WebSocket handshake is an HTTP request, so the browser auto-attaches cookies — and the Same-Origin Policy that protects fetch does not apply. If your server authenticates by cookie alone and skips the Origin check, any site can open an authenticated socket as your logged-in user. Step through the attack, then the fix.

Attack → defense walkthrough
STEP 1Victim is logged into bank.com; a session cookie sits in their browser.
STEP 2Victim visits evil.com (phishing, ad, anything).
STEP 3evil.com JS runs new WebSocket("wss://bank.com/api").
STEP 4Browser attaches bank.com cookies to the handshake. No SOP block.
STEP 5Server sees a valid session → evil.com now reads/sends as the victim. ☠

Fix #1 — check Origin

Reject handshakes whose un-forgeable Origin isn't allow-listed. First and cheapest line of defense.

Fix #2 — token, not ambient cookie

Require an explicit auth token (CSRF-style or JWT) the attacker can't read cross-origin. Browser WS can't set an Authorization header, so send the token in the first message or via subprotocol — avoid query strings (they get logged).

Resource-exhaustion DoS

Connections are cheap to open, expensive to hold. Defenses: per-IP connection + rate limits, handshake timeout, auth before allocating buffers, max message size, ping-timeout reaping.

Validate length before allocating

A frame can claim a 64-bit length of gigabytes. Never pre-allocate from the claim. Same for permessage-deflate: cap the decompressed size or a tiny frame becomes a memory bomb.

Part 14 — Performance Engineering

What does a connection actually cost?

Every connection consumes a file descriptor, two kernel socket buffers, and some application state. Multiply by your connection count and the answer is concrete hardware. Drive the model below — the presets reproduce the canonical 100K / 1M / 10M figures.

Live resource calculator
Estimates. CPU assumes ~2 µs/message (syscall + mask/unmask + parse + a little TLS); real numbers depend on TLS, compression, and batching. The point is the shape: memory and fds dominate the connection count; CPU and bandwidth dominate the message rate.

File-descriptor wall

Default ulimit -n is 1024. You must raise per-process nofile and system fs.file-max above your connection count, or you hit "too many open files" at exactly 1024 conns.

Buffer tuning is mandatory

Untuned tcp_rmem/wmem (100s of KB each) × 1M conns = 100s of GB. Shrink them and lean on autotuning — trade per-connection throughput for connection density.

Ephemeral-port ceiling

An LB/proxy making upstream connections is capped at ~64K per (dst IP, dst port) tuple. Spread across more backends/ports, or you starve ports before memory.
