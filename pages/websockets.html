Real Problems — and Why the Naive Solution Fails

K8s Pod Termination — the Full 90-Second Window

T+0s
K8s marks pod Terminating
Pod removed from Service Endpoints. Propagation to HAProxy and kube-proxy begins (async, takes 1–10s).
T+0s (concurrent)
preStop hook executes: sleep 15
Pod is still accepting connections. HAProxy may still route to it. This is intentional — new arrivals during propagation window get served, not dropped.
T+5–10s
HAProxy stops routing new connections to this pod
Its health check sees /readyz → 503 (we set draining=true at T+0 on SIGTERM, but SIGTERM hasn't arrived yet). Actually: /readyz still returns 200 during preStop because our Go process hasn't received SIGTERM yet — we just sleep. HAProxy's active check interval (2s) will see a failed check only if the pod became unhealthy. This is fine — the endpoint removal is the routing gate.
T+15s
SIGTERM arrives at Go process
Manager.Wait() unblocks. Sets draining=true. /readyz now returns 503. HTTP upgrade handler returns 503 for any new WS attempts (should be none at this point).
T+15–20s
Additional propagation safety sleep (5s inside Go)
Extra margin in case any HAProxy instance hasn't processed the endpoint removal yet.
T+20s
cancelHub() called — Hub drains all connections
Hub.drainAll() sends WebSocket CloseMessage (code 1001 "Going Away") to every connected client. Clients receive this, close their side, and reconnect via their backoff logic to a different pod.
T+20–50s
WaitGroup drains
Each writePump goroutine exits after seeing its send channel closed. The WaitGroup counter reaches zero as connections close.
T+50s (best case)
Process exits cleanly (exit 0)
Well within terminationGracePeriodSeconds=90. K8s sees clean exit, no SIGKILL needed.
T+90s (wall)
SIGKILL — hard limit
If drain doesn't complete in time, K8s sends SIGKILL. Remaining connections are dropped with TCP RST. Clients reconnect. This is acceptable for stuck connections but should not happen in normal operation.

Client-Side Reconnect Strategy (must implement for zero perceived downtime)

// Browser-side reconnect (TypeScript)
// The server sends CloseMessage 1001 during drain.
// The client must reconnect with exponential backoff.

class ReconnectingWebSocket {
  private ws: WebSocket | null = null;
  private attempt = 0;
  private maxDelay = 30_000; // 30 seconds max backoff

  connect() {
    this.ws = new WebSocket(`wss://yourapp.com/ws?user_id=${userId}&room_id=${roomId}`);

    this.ws.onclose = (event) => {
      if (event.code === 1001) {
        // Server going away (drain). Reconnect immediately once.
        setTimeout(() => this.connect(), 100);
        return;
      }
      // Exponential backoff: 1s, 2s, 4s, 8s… up to 30s
      const delay = Math.min(1000 * 2 ** this.attempt, this.maxDelay);
      this.attempt++;
      setTimeout(() => this.connect(), delay);
    };

    this.ws.onopen = () => { this.attempt = 0; }; // reset backoff on success
  }
}
