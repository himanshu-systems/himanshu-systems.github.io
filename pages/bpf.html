01 The wall

Everything worth knowing is on the wrong side

Your CPU enforces two privilege levels in hardware. Ring 3 code that touches kernel memory doesn't get a permission error, it faults. This isn't policy, it's the MMU.

  • Its own memory, and nothing else
  • Syscalls, and whatever they choose to return
/proc · /sys · netlink

RING 0 · KERNEL

  • Which process opened which file
  • How long every disk request took
  • Every packet, before reassembly
  • Why a thread waited 40ms to be scheduled
  • Which pages are being thrashed

enforced by hardware, not by convention

That slot in the wall is the sanctioned view: pre-aggregated counters someone decided to expose years ago, with the context stripped off. You can learn that 12,000 disk requests happened. You cannot learn which process issued the slow ones.

02 The old answers

Safe and useless, or powerful and lethal

July 2024: a bad config update to a kernel-level agent bluescreened millions of machines and recovery meant physically touching each one. That is the cost of no seatbelt in ring 0, and it's why the third column of these cards matters.

03 The dodge

Refuse the problem as stated

The question looks impossible. Deciding whether arbitrary code terminates is undecidable. You cannot inspect an arbitrary program and prove it safe.

So eBPF doesn't try. It defines a deliberately crippled language where the safety properties are decidable by construction, and rejects everything outside it.

Each restriction is a price, not a quirk

You are not writing C that runs in the kernel. You're writing a small hostile language with C-shaped syntax, and a static analyzer decides whether each program is allowed anywhere near ring 0.

04 The verifier

Watch it learn

The verifier does abstract interpretation. It simulates your program without running it, tracking not values but what it knows about each register: the type, and the range.

This reframes every verifier error you'll ever hit. It isn't saying your code is wrong. It's saying it cannot prove your code is safe from what you've shown it. Your if statements are how it learns facts, which is why you often add a check you personally know can never fail.

It's sound but not complete: it never accepts an unsafe program, but it does reject safe ones. That asymmetry is correct. A false rejection annoys a developer. A false acceptance panics a datacenter.

05 Lifecycle

Source to native code

Worth knowing up front: eBPF is not interpreted in production. The virtual machine is a verification target, not an execution strategy.

The instruction set was designed to look like real 64-bit hardware, so translating it to x86-64 or arm64 is close to one-to-one. That's why a BPF program costs tens of nanoseconds rather than microseconds.

06 Maps

The only channel through the wall

Your program can't allocate memory, has a 512-byte stack, and forgets everything when it returns. Maps are the fix: key-value structures in kernel memory, sized before load, reachable from both sides.

And helpers

Your program can't call arbitrary kernel functions, that would destroy the whole safety argument. It calls from a whitelist whose signatures the verifier knows exactly. That's why you're forced to null-check a map lookup: the verifier marks the returned register as "pointer that may be NULL" and refuses any use until you've branched on it.

07 Attachment

Where programs plug in

A program is inert until it's wired somewhere execution passes through. Earlier in a path means less work already wasted, which is why XDP can drop at line rate.

08 CO-RE

One binary, every kernel

When you write task->real_parent, the compiler emits "load from pointer + 0x898". It baked in an offset it read from a struct definition. But that struct is laid out differently on every kernel build, so on the next machine that offset silently points at a different field. Not a crash. Garbage.

Modern kernels publish their own type layout as BTF at /sys/kernel/btf/vmlinux. Clang emits a relocation record saying "this instruction loads field real_parent," and at load time libbpf reads the running kernel's BTF and rewrites the offset before the verifier ever sees it.

The old fix was to ship Clang, LLVM, Python and kernel headers to every production box and compile on startup. That's what CO-RE replaced, and why libbpf displaced BCC for anything you intend to ship.

09 Why it matters

The link that got broken

For thirty years, "change kernel behavior" meant "accept the risk of kernel code." Those were welded together. eBPF separated them.

The price is that you write in a small hostile language and argue with a static analyzer. The payoff is that a bad program fails to load instead of taking down a fleet.

That's also why the trajectory keeps going. Packet filtering, then observability, then networking, then security enforcement, and now with struct_ops it replaces kernel policy wholesale: TCP congestion control, device quirks, and entire CPU schedulers via sched_ext. It's becoming the kernel's general-purpose extension ABI.

Best next move: take a working program, break it deliberately, and read each rejection. Delete a null check after a map lookup. Remove a bounds check. Write a loop the verifier can't bound. Two hours of that teaches the verifier better than any explainer, this one included.
