The Problem

Why Consensus Exists

You have a key-value store. Your app writes x = 5. You replicate it to 3 servers for fault tolerance. Now Server 2 crashes mid-write and comes back online. Server 1 got the write. Server 3 didn't. What is x? Nobody agrees.

Raft solves this by ensuring all servers apply commands in the same order. It does this through a replicated log. Every command goes into the log first. Once a log entry is safely stored on a majority, it is committed and applied to the state machine. The result: identical state on every server, even across crashes.

All that extra code after line 500 is error handling, batching, flow control, membership changes, and snapshotting. The algorithm itself is the first 500. Let's build it from zero.

Section 01 — The Foundation

The State Every Node Holds

Every server in a Raft cluster runs the exact same binary. There is no special "leader binary" — just one program, and the leader role is a runtime value in this struct. Understand every field here and you're 70% done.

raft.go
// LogEntry is one record in the replicated log.
type LogEntry struct {
    Term    int         // which leader term created this entry
    Command interface{} // opaque command for the state machine
}

// Raft is one node. Every node in the cluster runs this same struct.
type Raft struct {
    mu    sync.Mutex
    peers []*labrpc.ClientEnd // RPC handles to all peers (including self)
    me    int               // our own index in peers[]

    // ─── PERSISTENT state ─────────────────────────────────────────────────
    // These three fields MUST be written to disk before replying to any RPC.
    // If we crash and restart without them, we could vote twice in one term
    // or lose committed entries — both catastrophic.
    currentTerm int        // latest term seen (starts 0, only increases)
    votedFor    int        // peer we voted for this term (-1 = nobody)
    log         []LogEntry // the log; log[0] is a sentinel; real entries at 1+

    // ─── VOLATILE state on ALL servers ───────────────────────────────────
    commitIndex int // highest index known to be committed (safe on majority)
    lastApplied int // highest index applied to the state machine

    // ─── VOLATILE state on LEADERS only (reset after every election) ─────
    nextIndex  []int // for each peer: next log index to send them
    matchIndex []int // for each peer: highest index confirmed on that peer

    // ─── Housekeeping ────────────────────────────────────────────────────
    role          Role
    electionTimer time.Time // last valid contact from leader or granted vote
    applyCh       chan ApplyMsg // committed entries go here for the app layer
}

type Role int
const (
    Follower  Role = iota
    Candidate
    Leader
)
Key insight — commitIndex vs lastApplied

commitIndex = "safe on a majority, will never be lost." lastApplied = "actually executed on this machine's state machine." Commitment is a distributed agreement; applying is a local, lazy operation. They're always lastApplied ≤ commitIndex.

Why persist currentTerm, votedFor, log — and nothing else?

These are the only things you can't reconstruct after a crash. commitIndex and lastApplied can be rebuilt from the persisted log on restart. nextIndex and matchIndex are leader-only guesses that reset after every election anyway.

Section 02 — Leader Election

How a Leader Is Born

Every follower has an election timer. If it doesn't hear from a leader before that timer fires, it assumes the leader is dead and stands for election. The timer is randomized (150–300 ms) — this is what prevents all nodes timing out simultaneously and splitting votes forever.

Press Play to watch a leader election unfold.

startElection() — line by line

When the election timer fires, the node calls startElection() while holding the mutex. The four mutations at the top are an atomic unit that must survive to disk before sending any RPC.

election.go
// Called under rf.mu. Increments term, votes for self, fires RPCs.
func (rf *Raft) startElection() {
    rf.currentTerm++          // enter a new term — we're claiming a new era
    rf.role = Candidate
    rf.votedFor = rf.me       // vote for ourselves
    rf.resetElectionTimer()
    rf.persist()             // ← MUST hit disk before sending any RPC
                              //   Without this, a crash here could lose our vote
    term         := rf.currentTerm
    lastLogIndex := len(rf.log) - 1
    lastLogTerm  := rf.log[lastLogIndex].Term
    votes        := 1         // counting our own vote

    for peer := range rf.peers {
        if peer == rf.me { continue }
        go func(peer int) {   // send RPCs in parallel — never block the main loop
            args := RequestVoteArgs{
                Term:         term,
                CandidateId:  rf.me,
                LastLogIndex: lastLogIndex,
                LastLogTerm:  lastLogTerm,
            }
            var reply RequestVoteReply
            if !rf.sendRequestVote(peer, &args, &reply) {
                return // RPC lost/peer down — drop it, move on
            }
            rf.mu.Lock()
            defer rf.mu.Unlock()

            // Rule A: if we see a higher term, step down immediately
            if reply.Term > rf.currentTerm {
                rf.becomeFollower(reply.Term)
                return
            }
            // Rule B: stale-reply guard — replies can arrive after we moved on
            if rf.role != Candidate || rf.currentTerm != term {
                return
            }
            if reply.VoteGranted {
                votes++
                if votes > len(rf.peers)/2 { // strict majority
                    rf.becomeLeader()
                }
            }
        }(peer)
    }
}

RequestVote handler — the up-to-date check

The receiver is where Raft's main safety guarantee lives. A server will only vote for a candidate whose log is at least as up-to-date as its own. This single check is why a new leader always has every committed entry.

election.go
func (rf *Raft) RequestVote(args *RequestVoteArgs, reply *RequestVoteReply) {
    rf.mu.Lock()
    defer rf.mu.Unlock()
    defer rf.persist() // votedFor may change — persist before returning

    reply.Term = rf.currentTerm

    // Rule 1: reject stale candidates
    if args.Term < rf.currentTerm {
        reply.VoteGranted = false
        return
    }
    // Rule 2: candidate is in a newer term → step down, adopt it
    if args.Term > rf.currentTerm {
        rf.becomeFollower(args.Term) // also clears votedFor for the new term
    }
    reply.Term = rf.currentTerm

    // Rule 3: THE ELECTION RESTRICTION — up-to-date check
    // Compare last entries: higher term wins; tie → longer log wins.
    // A candidate missing committed entries WILL be rejected here.
    myLast     := len(rf.log) - 1
    myLastTerm := rf.log[myLast].Term
    logOK := args.LastLogTerm > myLastTerm ||
        (args.LastLogTerm == myLastTerm &&
            args.LastLogIndex >= myLast)

    // Rule 4: one vote per term — votedFor must be empty or already this candidate
    if (rf.votedFor == -1 || rf.votedFor == args.CandidateId) && logOK {
        rf.votedFor = args.CandidateId
        rf.resetElectionTimer() // valid candidate contact — reset our timer
        reply.VoteGranted = true
    } else {
        reply.VoteGranted = false
    }
}
Election Restriction — why it guarantees safety

A committed entry is on a majority of servers. To win, a candidate needs a majority of votes. Those two majorities must overlap in at least one server. That server has the committed entry and will refuse to vote for any candidate missing it. So every elected leader is guaranteed to already have every committed entry — no transfer needed.

Section 03 — Log Replication

How Commands Spread Across the Cluster

Once a leader exists, clients send commands to it. The leader appends the command to its log and then replicates it to every follower via AppendEntries RPCs. When a strict majority has stored the entry, the leader commits it and applies it to the state machine.

Press Play to watch log replication and commitment.

Leader sends AppendEntries

replication.go
// broadcastAppendEntries runs on the leader. When entries is empty it's a heartbeat.
func (rf *Raft) broadcastAppendEntries() {
    for peer := range rf.peers {
        if peer == rf.me { continue }
        go func(peer int) {
            rf.mu.Lock()
            if rf.role != Leader { rf.mu.Unlock(); return }

            ni       := rf.nextIndex[peer]       // leader's guess of follower's position
            prevIdx  := ni - 1
            prevTerm := rf.log[prevIdx].Term
            entries  := make([]LogEntry, len(rf.log[ni:]))
            copy(entries, rf.log[ni:])          // snapshot under the lock
            args := AppendEntriesArgs{
                Term:         rf.currentTerm,
                LeaderId:     rf.me,
                PrevLogIndex: prevIdx,   // junction point for consistency check
                PrevLogTerm:  prevTerm,
                Entries:      entries,
                LeaderCommit: rf.commitIndex,
            }
            rf.mu.Unlock()

            var reply AppendEntriesReply
            if !rf.sendAppendEntries(peer, &args, &reply) { return }

            rf.mu.Lock(); defer rf.mu.Unlock()
            if reply.Term > rf.currentTerm { rf.becomeFollower(reply.Term); return }
            if rf.role != Leader { return } // stale-reply guard

            if reply.Success {
                newMatch := args.PrevLogIndex + len(args.Entries)
                if newMatch > rf.matchIndex[peer] {
                    rf.matchIndex[peer] = newMatch
                    rf.nextIndex[peer]  = newMatch + 1
                    rf.maybeAdvanceCommit() // might be able to commit now
                }
            } else {
                // Log inconsistency — back up and retry next heartbeat
                if rf.nextIndex[peer] > 1 {
                    rf.nextIndex[peer]--
                }
            }
        }(peer)
    }
}

Follower receives AppendEntries — the consistency check

replication.go
func (rf *Raft) AppendEntries(args *AppendEntriesArgs, reply *AppendEntriesReply) {
    rf.mu.Lock(); defer rf.mu.Unlock()
    defer rf.persist()
    reply.Term    = rf.currentTerm
    reply.Success = false

    // Rule 1: reject stale leaders
    if args.Term < rf.currentTerm { return }

    // Rule 2: valid leader contact — stay/become follower
    rf.becomeFollower(args.Term)
    rf.resetElectionTimer()

    // Rule 3: LOG MATCHING CHECK
    // Do I have an entry at prevLogIndex with the matching term?
    // This is the inductive guarantee: if the junction matches, the entire
    // prefix up to that point is identical on both leader and follower.
    if args.PrevLogIndex >= len(rf.log) ||
        rf.log[args.PrevLogIndex].Term != args.PrevLogTerm {
        return // mismatch: leader will decrement nextIndex and retry
    }

    // Rule 4: reconcile entries — only overwrite actual conflicts, not clean matches
    // This matters for out-of-order/duplicate RPCs: a late heartbeat shouldn't
    // truncate entries the follower already correctly received.
    for i, entry := range args.Entries {
        idx := args.PrevLogIndex + 1 + i
        if idx < len(rf.log) {
            if rf.log[idx].Term != entry.Term {     // conflict found
                rf.log = rf.log[:idx]               // truncate from here
                rf.log = append(rf.log, args.Entries[i:]...)
                break
            }
        } else {
            rf.log = append(rf.log, args.Entries[i:]...)
            break
        }
    }

    // Rule 5: advance our commit index toward the leader's
    if args.LeaderCommit > rf.commitIndex {
        rf.commitIndex = min(args.LeaderCommit, len(rf.log)-1)
        rf.applyEntries()
    }
    reply.Success = true
}
Section 04 — The Safety Rules

What Keeps It Correct

Raft has two rules that most people miss on a first read. Miss either one and you can silently corrupt data in a way that looks fine for months.

Rule 1 — The Figure 8 trap (commit only current-term entries)

A leader may not commit an entry from a previous term just because it's now on a majority. It can only commit entries from its current term by counting replicas. Entries from older terms get committed as a side-effect, implicitly, via the Log Matching Property.

safety.go
func (rf *Raft) maybeAdvanceCommit() {
    for N := len(rf.log) - 1; N > rf.commitIndex; N-- {

        // ★ THE CRITICAL RULE (Figure 8 in the paper):
        //   Only count replicas for entries created in OUR term.
        //   Without this, a replicated entry from term 4 looks safe but
        //   a new leader in term 5 can legally overwrite it.
        //   By requiring currentTerm, we ensure "safe" actually means safe.
        if rf.log[N].Term != rf.currentTerm {
            continue
        }

        replicas := 1 // count ourselves
        for peer := range rf.peers {
            if peer != rf.me && rf.matchIndex[peer] >= N {
                replicas++
            }
        }
        if replicas > len(rf.peers)/2 {
            rf.commitIndex = N
            rf.applyEntries()
            break // all entries before N get committed implicitly (Log Matching)
        }
    }
}

// applyEntries sends committed-but-not-yet-applied entries to the app.
func (rf *Raft) applyEntries() {
    for rf.lastApplied < rf.commitIndex {
        rf.lastApplied++
        msg := ApplyMsg{
            CommandValid: true,
            Command:      rf.log[rf.lastApplied].Command,
            CommandIndex: rf.lastApplied,
        }
        // Release the lock before sending to applyCh to avoid deadlock
        go func(m ApplyMsg) { rf.applyCh <- m }(msg)
    }
}
The Figure 8 scenario — what breaks without this rule

Leader A (term 2) replicates entry [term:2] on 3 servers, then crashes before committing. Leader B (term 3) wins with a different log tail. It could overwrite that entry even though 3 servers had it — because "on a majority" without log[N].term == currentTerm doesn't mean committed. The rule forces you to get a current-term entry onto a majority first, which implicitly locks in all prior entries.

Rule 2 — Stale-reply guard (appears in every RPC handler)

Goroutines send RPCs while not holding the lock. By the time a reply arrives, the world may have moved on — a new term started, we stopped being candidate. Every reply handler must check:

// Pattern that appears in EVERY RPC reply handler:

// Ignore the reply if our state has changed since we sent the RPC.
// A "yes" vote from term 5 that arrives when we're now in term 7 is useless.
if rf.role != expectedRole || rf.currentTerm != sentTerm {

Section 05 — Crash Recovery

Surviving a Server Restart

Three fields must be written to stable storage before replying to any RPC that touches them. If a server crashes with a stale currentTerm or votedFor on disk, it can vote twice in the same term — potentially electing two leaders. If it crashes with a truncated log, it permanently loses committed entries.

persist.go
// persist serializes the three critical fields and hands them to the persister.
// This MUST be called (via defer) at the end of any handler that modifies
// currentTerm, votedFor, or log.
func (rf *Raft) persist() {
    w := new(bytes.Buffer)
    e := labgob.NewEncoder(w)
    e.Encode(rf.currentTerm)
    e.Encode(rf.votedFor)
    e.Encode(rf.log)
    rf.persister.SaveRaftState(w.Bytes())
}

// readPersist restores state from disk on startup after a crash.
func (rf *Raft) readPersist(data []byte) {
    if data == nil || len(data) < 1 { return }
    r := bytes.NewBuffer(data)
    d := labgob.NewDecoder(r)
    var term     int
    var votedFor int
    var log      []LogEntry
    if d.Decode(&term)     != nil ||
       d.Decode(&votedFor) != nil ||
       d.Decode(&log)      != nil {
        panic("persist: decode failed")
    }
    rf.currentTerm = term
    rf.votedFor    = votedFor
    rf.log         = log
    // commitIndex and lastApplied start at 0 — rebuilt by replaying the log
}

// The ticker drives everything. Followers check for election timeout.
// Leaders send heartbeats. 10ms sleep gives us ~100 checks/sec granularity.
func (rf *Raft) ticker() {
    for !rf.killed() {
        time.Sleep(10 * time.Millisecond)
        rf.mu.Lock()
        switch rf.role {
        case Follower, Candidate:
            timeout := 150 + rand.Intn(150) // 150–300ms, randomized
            if time.Since(rf.electionTimer) > time.Duration(timeout)*time.Millisecond {
                rf.startElection()
            }
        case Leader:
            rf.broadcastAppendEntries() // sends heartbeats + any pending entries
        }
        rf.mu.Unlock()
    }
}
