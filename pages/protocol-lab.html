Wire protocol → implementation

The one idea that explains everything

Every jump — HTTP/1.1 → HTTP/2 → HTTP/3 — is a fight against head-of-line blocking. Each version kills it at one layer and exposes it at the next. Watch the packets move and you'll never forget where each protocol wins and loses.

One lost packet, three protocols

A server sends one red, one cyan, one amber resource at the same time. The 3rd packet is lost. Hit play and watch what gets stuck. This little loop is the whole course in 6 seconds.

Stream A Stream B Stream C blocked / waiting
HTTP/1.1
6 TCP connections

One resource per connection at a time. No app-layer multiplexing, so people opened ~6 sockets and invented domain sharding, spriting, inlining. A lost packet only stalls its own connection — but you're capped at 6 things in flight and pay a handshake for each.

HTTP/2
1 TCP connection

Many streams multiplexed as binary frames over one TCP stream. Fixes app-layer blocking — but TCP still delivers one ordered byte stream, so one lost segment freezes every stream. This is the flaw HTTP/3 exists to fix.

HTTP/3
QUIC over UDP

QUIC runs in user space over UDP and tracks loss per stream. A lost packet only stalls its own stream; the others keep being delivered to the page. It also fuses the TLS 1.3 handshake into the transport handshake.

The twist

It's not free. QUIC's user-space, per-packet crypto + ACK processing costs roughly 2× the CPU and can be up to 45.2% slower than HTTP/2 on a 1 Gbps link. HTTP/3 is a win for the slow tail of users, not a universal speedup.

Module 01

Head-of-Line Blocking Lab

Pick a protocol, fire a packet loss, and watch exactly which streams stall and which keep flowing. Same loss, three very different outcomes.

Stream A Stream B Stream C Stream D HOL-blocked retransmit
Mode: HTTP/1.1 — 6 independent TCP connections. A drop on one connection never blocks the others, but only 6 resources move at once.

What you're seeing

HTTP/2: all streams ride one ordered TCP byte stream. When a segment is lost, TCP refuses to deliver any later bytes to the app until the retransmit lands — so cyan/amber/green packets that already arrived sit in the kernel buffer, greyed out. That's transport-layer HOL blocking.

HTTP/3: QUIC carries an explicit Stream ID per frame and recovers loss per stream. Only stream A waits for its retransmit; B, C, D are delivered to the page immediately.

Single-loss impact

ProtocolStreams stalled by 1 loss
HTTP/1.1 (6 conns)1 of 6 connections
HTTP/2 (1 conn)ALL multiplexed streams
HTTP/3 (QUIC)only the affected stream

TCP guarantees in-order delivery of a single byte stream: byte N+1 is never handed up before byte N. That guarantee is the source of HTTP/2's blocking — and QUIC sidesteps it by giving each stream its own delivery order.

Slow start: cwnd starts at the initial window (10 MSS) and doubles each RTT — exponential growth until the first loss or ssthresh.

The three reactions

CUBIC (Linux/Win/macOS default): on loss, multiply window by β=0.7 (a 30% cut), then regrow along a cubic curve in time since loss — RTT-independent, so flows with different RTTs stay fair. W(t)=C·(t−K)³+W_max, C=0.4.

Reno: classic AIMD — halve on loss (×0.5), then add 1 MSS per RTT. Gentle but slow to refill a fat pipe.

BBR: ignores loss as a signal. Models bottleneck bandwidth × min-RTT and paces at the BDP. Keeps throughput high on lossy links where CUBIC collapses — the reason it matters for mobile.

RTO & retransmit math (RFC 6298)

Loss is detected two ways: 3 duplicate ACKs → fast retransmit (no waiting), or the retransmission timeout fires. The RTO is built from a smoothed RTT and its variance:

RTTVAR = ¾·RTTVAR + ¼·|SRTT − R|
SRTT   = ⅞·SRTT   + ⅛·R
RTO    = SRTT + max(G, 4·RTTVAR)

α=⅛, β=¼, K=4. Order matters — RTTVAR is updated before SRTT. RTO is floored at 1 second. A fat-pipe rule of thumb: 10 Gbps at 100 ms RTT with CUBIC needs packet loss below ~0.000003%.

Why HTTP/3 is exactly 1 RTT faster

The honest comparison is against a modern stack. TCP+TLS 1.3 is already 2 RTT. QUIC folds the crypto handshake into the transport handshake, saving one round trip → 1 RTT. On a resumed connection with a cached PSK it sends application data in the very first flight → 0-RTT. The "2–3 RTT faster" headline only holds versus the older TLS 1.2 stack.

0-RTT data is replayable and lacks forward secrecy, so it's restricted to idempotent requests (GET, not "transfer $100").

ALPN & why TLS 1.3 is mandatory in H3

ALPN negotiates the protocol — h2 or h3 — inside the TLS handshake, with no extra round trip. QUIC requires TLS 1.3 because it has no separate TLS record layer: it pulls per-encryption-level secrets straight from the TLS 1.3 key schedule (HKDF). TLS 1.2's design simply can't export those keys cleanly.

Module 04

Multiplexing & the Scheduler

Multiplexing is a scheduling problem: N streams share one pipe of bandwidth B. How you interleave their frames changes when each resource finishes.

Round-robin: each stream gets B/N. Everything progresses in parallel but everything also finishes late — a half-downloaded JS file is useless, so this is often the wrong default for the web.

Why browsers abandoned the HTTP/2 priority tree

RFC 7540 let every stream declare a parent, a weight (1–256), and an exclusive flag — a full weighted dependency tree. In practice the three engines built radically different trees: Firefox used phantom grouping nodes, Chrome used a mostly-linear sequential order, Safari differed again. Servers couldn't honor all of them well, so RFC 9113 deprecated the whole scheme.

The replacement, RFC 9218 Extensible Priorities, is just two signals in a header: urgency (u=0–7, default 3) and incremental (boolean, default false). Send the lowest urgency-number group first; interleave incremental resources, serve non-incremental ones one at a time. Simple enough that implementations actually agree.

RFC 7540 dependency tree — deprecated RFC 9218 urgency + incremental — current

Connection opens with the magic preface PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n followed by a SETTINGS frame. Client streams are odd, server-pushed streams even. The exact SETTINGS order + a WINDOW_UPDATE delta of 15,663,105 is now used to fingerprint Chrome.

HPACK IN ONE BREATH

Headers compress via a 61-entry static table + a per-connection FIFO dynamic table (default 4096 B; entry size = name+value+32). Integers use prefix coding; strings use a fixed static Huffman code. The static (not adaptive) code is deliberate: it denies CRIME-style compression oracles. Sensitive values use the never-indexed literal so they never enter the table.

Module 06

QUIC Packet Anatomy

QUIC has two header forms and a clever variable-length integer. Toggle between them — these are the bytes Wireshark removes header-protection from before it can show you anything.

Tap a field

Long headers carry the version + connection IDs and are used during setup (Initial / Handshake / 0-RTT / Retry). Short headers are the steady-state 1-RTT data packets.

Variable-length integers (RFC 9000 §16)

The 2 most-significant bits of the first byte pick the encoding length. One scheme covers values from 0 to 2⁶²−1:

2 MSBLengthRange
001 byte0 – 63
012 bytes0 – 16383
104 bytes0 – 2³⁰−1
118 bytes0 – 2⁶²−1

Packets vs frames vs spaces

A UDP datagram carries one+ QUIC packets (coalesced); each packet carries one+ frames (STREAM, ACK, CRYPTO, PADDING, …). Packet numbers live in three separate spaces — Initial, Handshake, Application — each numbered independently from 0.

Crucially, a retransmitted frame goes in a new packet number, so QUIC never has TCP's "is this ACK for the original or the retransmit?" ambiguity. Long packet types: Initial 0x0, 0-RTT 0x1, Handshake 0x2, Retry 0x3.

Module 07

QUIC Key Derivation Flow

QUIC's Initial keys are derived from something the attacker can see — the client's Destination Connection ID — plus a fixed published salt. Press play to walk the HKDF chain step by step.

v1 salt is a constant in RFC 9001 §5.2 — Initial packets are "encrypted" but anyone can derive these keys; the point is integrity + obfuscation against dumb middleboxes, not secrecy. Real secrecy starts with Handshake keys (from ECDHE).

Two layers: payload then header

1. Packet protection — AEAD encrypts the payload; nonce = IV XOR packet-number; the cleartext header is the associated data.

2. Header protection — applied after. Sample 16 bytes of the ciphertext → mask = AES-ECB(hp_key, sample) → XOR the mask onto the first byte's low bits and the packet number. The hp key never rotates on key update, which is exactly why it can protect the Key Phase bit. Wireshark must undo this layer before it can show you the packet number at all.

Measured endpoints

High loss wins: at 12% loss with no proxy, a download took 113.42 s on HTTP/2 vs 20.98 s on HTTP/3 — an 81.5% improvement (arXiv 2409.16267). Beyond ~8% loss H3 pulls decisively ahead.

Fast network loses: "QUIC is not Quick Enough over Fast Internet" (ACM WWW 2024) measured QUIC up to 45.2% slower than HTTP/2 at 1 Gbps, and ~3–15% behind above ~600 Mbps — receiver-side per-packet processing and user-space ACKs are the bottleneck.

The rule of thumb

HTTP/3 is an evolution, not a revolution (Robin Marx). It mainly helps the slowest 1–10% of your audience: high-RTT mobile, lossy Wi-Fi, satellite. On low-RTT, low-loss fiber, HTTP/2 may still win and HTTP/3 costs ~2× CPU.

Loss-based CUBIC reads loss as congestion and throttles hard — so at 1% loss its throughput collapses while BBR and QUIC's per-stream recovery hold up. The "always use H3" advice is wrong for fast networks.
